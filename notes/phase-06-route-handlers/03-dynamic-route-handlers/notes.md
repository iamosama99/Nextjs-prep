# Dynamic Route Handlers & Params

**Demo:** `app/playground/phase-06-route-handlers/03-dynamic-route-handlers/api/` — run `npm run dev`, then
`curl` each path below. `generateStaticParams` behavior verified against a real `npm run build` (three
posts pre-generated with `●` SSG markers); the per-argument `"use cache"` caching verified by calling both
a pre-generated and a non-pre-generated post id twice each.

## Quick Reference

| You write / see | What it actually is | Why it matters |
|---|---|---|
| `app/api/items/[slug]/route.ts` | A Route Handler matching a dynamic segment, same convention as `page.tsx` (Phase 2 Topic 5) | Identical mental model — you already know this from pages |
| `{ params }: { params: Promise<{ slug: string }> }` | `params` is a **Promise** you must `await` | Same reason as dynamic page segments — Next can't guarantee it's resolved synchronously |
| `RouteContext<'/api/posts/[id]'>` | A typed-helper alternative to writing the params shape by hand | Strongly-typed `params` derived from the literal route path, generated by `next dev`/`build`/`typegen` |
| `generateStaticParams` in a `route.ts` | Pre-renders specific param combinations at build time | Verified: `●` (SSG) in the build output for pre-generated ids, still works (dynamically) for any other |

## Where Does This Run?

Same as any Route Handler (Topic 1): entirely server-side, per matching request. `generateStaticParams` itself runs once, at build time, to decide which param combinations get prerendered.

## What Is This?

Route Handlers use the exact same dynamic-segment file conventions as pages — `[slug]`, `[...slug]`, multiple bracketed segments in one path — first covered for pages in Phase 2 Topic 5. Nothing new to learn about the *folder naming*; what's specific to Route Handlers is how those segments arrive in the handler function itself: as a `params` object on a second argument, resolved from a `Promise`.

```ts
export async function GET(
  request: Request,
  { params }: { params: Promise<{ slug: string }> }
) {
  const { slug } = await params
}
```

> **Check yourself:** Is `params` in a Route Handler synchronous data or something you need to `await`?

## Why Does It Exist?

An API needs the same segment-matching flexibility a UI route has — `/items/[slug]`, `/shop/[tag]/[item]`, `/blog/[...slug]` — for exactly the same reasons: a single handler file serving every product, every category, every blog path, rather than one file per possible value. Route Handlers reuse the identical file-convention mechanism rather than inventing a separate routing syntax for API endpoints.

## How It Works

### Single, multiple, and catch-all segments — all verified

[`items/[slug]/route.ts`](../../../app/playground/phase-06-route-handlers/03-dynamic-route-handlers/api/items/%5Bslug%5D/route.ts) resolves one segment (`slug: "anything"` for `/items/anything`). [`shop/[tag]/[item]/route.ts`](../../../app/playground/phase-06-route-handlers/03-dynamic-route-handlers/api/shop/%5Btag%5D/%5Bitem%5D/route.ts) resolves two independent keys on the same `params` object. [`blog/[...slug]/route.ts`](../../../app/playground/phase-06-route-handlers/03-dynamic-route-handlers/api/blog/%5B...slug%5D/route.ts) resolves every remaining segment into an array — a request to `/blog/2024/09/my-post` returns `slug: ["2024", "09", "my-post"]`. All three behave exactly like their page-segment counterparts (Phase 2 Topics 5–6); the only new fact is that `params` arrives as a `Promise` here too, requiring the same `await` a dynamic page segment does.

### `RouteContext` — the typed-helper alternative

Instead of writing out `{ params }: { params: Promise<{ id: string }> }` by hand, `RouteContext<'/exact/route/literal'>` (globally available once types are generated by `next dev`, `next build`, or `next typegen`) gives strongly-typed `params` derived directly from the route's own literal path — [`posts/[id]/route.ts`](../../../app/playground/phase-06-route-handlers/03-dynamic-route-handlers/api/posts/%5Bid%5D/route.ts) uses this form. Both styles work identically at runtime; `RouteContext` just removes the need to keep a hand-written type in sync with the folder structure.

### `generateStaticParams` — pre-rendering specific responses, verified

`generateStaticParams`, already familiar from Phase 3 Topic 8's page-segment treatment, works the same way for Route Handlers: return an array of param combinations, and Next.js prerenders a response for each at build time. `posts/[id]/route.ts` returns `{ id: '1' }`, `{ id: '2' }`, `{ id: '3' }` — confirmed directly against a real `npm run build`: all three classify `●` (SSG) with the `30d`/`1y` revalidate/expire window matching `cacheLife('max')` (Phase 3 Topic 6). A request for an id *not* in that list (`/posts/999`) still works correctly — `dynamicParams` defaults to `true`, so it falls through to on-demand rendering instead of 404ing, exactly the page-segment default (Phase 3 Topic 8).

### `"use cache"` still can't sit directly in the exported handler

Consistent with Topic 1: the cached logic lives in an extracted `getPost` helper, not inline in `GET` itself. Verified concretely that this caching is keyed by argument, independent of whether that specific id was one of the build-time pre-generated ones: calling `/posts/1` (pre-generated) twice returns an identical `generatedAt` timestamp both times, and calling `/posts/999` (not pre-generated, rendered dynamically on first request) *also* returns an identical timestamp on a second call — the `"use cache"` entry for `id: "999"` gets created and reused on its own, the same mechanism, regardless of build-time pre-generation status.

## Gotchas

- **`params` is always a `Promise` in a Route Handler**, exactly like a dynamic page segment — forgetting the `await` is the same class of mistake covered in Phase 2 Topic 5, just resurfacing here.
- **A catch-all's `params` value is an array, not a string** — `slug: string[]`, not `slug: string`, easy to get wrong when copy-pasting from a single-segment handler.
- **`RouteContext` requires generated types to exist** — it's populated by `next dev`, `next build`, or `next typegen`; a fresh checkout with no prior type generation and an editor that hasn't triggered it yet may show the helper as unresolved until one of those runs.
- **A param id outside `generateStaticParams`'s list isn't a 404 by default** — it's handled dynamically instead, because `dynamicParams` defaults to `true`. Explicitly wanting a 404 for anything not pre-generated requires setting `dynamicParams = false` under the previous caching model — under Cache Components (this project's configuration), that option is removed entirely (Phase 3 Topic 11); `notFound()` inside the handler is the replacement.

## Interview Questions

**Q (High): In a Route Handler for `app/shop/[tag]/[item]/route.ts`, what shape does `params` resolve to for a request to `/shop/electronics/laptop`, and what do you have to do before reading its fields?**

Answer: `params` resolves (after being `await`-ed, since it arrives as a `Promise`) to `{ tag: "electronics", item: "laptop" }` — one key per bracketed segment in the file path. The `await` is required regardless of how many segments are involved; it's not specific to single-segment routes.

The trap: forgetting `params` is a `Promise` and trying to destructure it synchronously, the same mistake covered for dynamic page segments in Phase 2.

**Q (High): A Route Handler at `app/api/posts/[id]/route.ts` defines `generateStaticParams` returning three ids. What happens when a request arrives for an id not in that list?**

Answer: It's still handled — rendered dynamically on demand rather than returning a 404 — because `dynamicParams` defaults to `true`. The three listed ids get prerendered at build time (verified: they classify `●`/SSG in the build output); any other id falls through to per-request rendering instead of being rejected.

The trap: assuming `generateStaticParams` implicitly restricts the route to only the listed values, when by default it only controls what gets prerendered ahead of time, not what's considered valid.

**Q (Medium): What's the actual difference between writing `{ params }: { params: Promise<{ id: string }> }` by hand versus using `RouteContext<'/api/posts/[id]'>`?**

Answer: Functionally nothing at runtime — both resolve to the same `params` Promise. `RouteContext` is a typing convenience: it derives the params shape directly from the route's literal path string (generated by `next dev`/`build`/`typegen`), so the type stays automatically in sync with the actual folder structure instead of being a hand-maintained type that could drift out of sync if the route's segments change.

The trap: treating `RouteContext` as adding new runtime capability, rather than recognizing it as purely a type-safety/maintenance improvement over writing the same shape manually.

**Q (Medium): If `getPost(id)` is wrapped in `"use cache"` and called from a Route Handler for an id that wasn't part of `generateStaticParams`'s build-time list, is that call still cached?**

Answer: Yes — verified directly. `"use cache"` caches by the function's arguments, independent of whether that particular argument value was among the ones prerendered at build time. A non-pre-generated id gets its cache entry created on its first request and reused on subsequent ones, the same mechanism as a pre-generated id, just created later (at request time instead of build time).

The trap: conflating "prerendered by `generateStaticParams`" with "the only cacheable inputs" — `"use cache"` caching and build-time static generation are related but distinct mechanisms; the former applies to any argument value, prerendered or not.

**Q (Low): Why can't `"use cache"` be placed directly on the exported `GET` function in a Route Handler?**

Answer: Same restriction covered in Topic 1 — `"use cache"` has to wrap a separate, extracted function that the handler calls, not the exported HTTP-method function itself. This is a Route-Handler-specific limitation of the directive, not something that applies to `"use cache"` in general UI code.

The trap: assuming the restriction is arbitrary rather than specific to the exported-handler-function context, and being surprised it doesn't apply the same way in a Server Component or a plain helper elsewhere.
